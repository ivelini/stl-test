# Шаг 3. Архитектурный стиль

- **Дата:** 2026-08-27
- **Статус:** согласовано
- **Метод:** «Head First. Архитектура ПО», гл. 5, гл. 6

Четвёртое измерение архитектуры. Стиль выбран после характеристик (шаг 1) и компонентов (шаг 2).

---

## 1. Решение

**Многоуровневая архитектура: монолитное развёртывание, техническая организация кода.**

Для Laravel этот стиль напрашивается сам собой. Фреймворк построен по MVC, а многоуровневая архитектура — его концептуальный двойник: каталоги `app/Http` / `app/Services` / `app/Models` уже являются уровнями представление / рабочий процесс / хранение, и жизненный цикл запроса проходит по ним сверху вниз: route → middleware → controller → service → model → БД. Стиль — нативная форма фреймворка.

Три уровня:

| Уровень | Содержимое |
|---|---|
| Представление | Приём запросов, проверка входных данных, форма ответа |
| Рабочий процесс | Сценарии и логические компоненты шага 2 |
| Хранение | Данные о слотах и удержаниях, кэш доступности |

Соответствие логических компонентов уровням:

| Компонент (шаг 2) | Уровень |
|---|---|
| Витрина доступности | Представление (приём запроса показа) + рабочий процесс (актуальность в пределах окна) |
| Выдача удержаний | Представление (приём команды) + рабочий процесс |
| Арбитраж вместимости | Рабочий процесс |
| Жизненный цикл удержания | Рабочий процесс + хранение (состояния билетов) |

---

## 2. Соответствие характеристикам

**Целостность данных (1).** Арбитраж вместимости работает в одном процессе: между решением о месте и его фиксацией нет сетевого звена, транзакционная граница одна.

**Масштабируемость (2).** Всплески чтения гасятся кэшем внутри монолита; распределение для этого не требуется.

**Осуществимость (3).** Стиль совпадает с нативной формой стека и со структурой классов, заданной в техническом задании. Дополнительной дисциплины стиль не требует — при сроке 10 дней это решающий довод.

---

## 3. Последствия

**Упростилось:**

- Реализация в срок: ноль трения со стеком, структура совпадает с заданной в ТЗ.
- Производительность: запрос проходит по уровням в одном процессе, сетевых вызовов внутри системы нет.
- Целостность: одна транзакционная граница для арбитража вместимости.

**Стало сложнее:**

- Масштабируемость «всё или ничего» — свойство монолитного развёртывания; в задаче снимается кэшем чтения.
- Изменение предметной области затрагивает все уровни; на горизонте задачи предметная область зафиксирована техническим заданием, поэтому слабость не проявляется.

**Путь эволюции:** при росте предметной области — переход к модульному монолиту по гл. 7; при росте нагрузки сверх характеристик монолита — пересмотр модели вместимости, а не разъезд в распределённые стили.
