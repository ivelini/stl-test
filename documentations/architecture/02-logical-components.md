# Шаг 2. Логические компоненты

- **Дата:** 2026-08-27
- **Статус:** согласовано
- **Метод:** «Head First. Архитектура ПО», гл. 4 (4 шага: выявление → назначение требований → анализ обязанностей → анализ характеристик; CA/CE/CT; закон Деметры)

Третье измерение архитектуры. Логическая архитектура **безразлична к БД, кэшу и протоколам** — физическое «приземление» произойдёт на шаге 5. Характеристики — шаг 1, решения — шаг 4.

---

## 1. Выявление компонентов

Подход — **рабочие процессы**, а не «субъекты и действия»: в системе один тип пользователя (клиент API), поэтому разбиение по субъектам ничего не разделяет; выражен процесс «посмотреть доступность → удержать → подтвердить или отказаться».

| Шаг процесса | Компонент | Обязанность |
|---|---|---|
| Клиент смотрит свободные места | **Витрина доступности** | Отдать представление остатков; отвечать за актуальность в пределах согласованного окна |
| Клиент получает билет на слот | **Выдача удержаний** | Создать удержание; обеспечить неизменность результата при повторе запроса |
| Клиент подтверждает бронь | **Арбитраж вместимости** | Единственный компонент, решающий, есть ли место. Хранитель доменного правила 6 |
| Клиент отказывается; время идёт | **Жизненный цикл удержания** | Переходы состояний билета: годен, подтверждён, отменён, просрочен |

Четыре компонента вместо одного супервизора. Заданное в ТЗ имя `SlotService` — ограничение физической реализации, на логическом уровне оно не обязано соответствовать одному компоненту (соответствие — на шаге 5).

**Ключевое разделение** — выдача удержаний отделена от арбитража вместимости: выдача обслуживает всех обращающихся и не является дефицитной, арбитраж сериализует конкурентов и несёт движущую характеристику 1. Слияние означало бы распространение точки сериализации на путь, который в ней не нуждается.

## 2. Назначение требований

| Требование (из шага 1) | Компонент-владелец | На языке компонента |
|---|---|---|
| Показ доступности | Витрина доступности | Отдавать остаток в форме `{slot_id, capacity, remaining}`; держать окно устаревания в согласованных пределах |
| Создание удержания | Выдача удержаний | Выдавать билет со сроком годности 5 минут; повтор запроса не создаёт второй билет |
| Отказ при исчерпании | Арбитраж вместимости | Единственный, кто решает «есть ли место» |
| Запрет перепродажи | Арбитраж вместимости | Инвариант: подтверждённых не больше вместимости |
| Подтверждение | Жизненный цикл удержания | Перевести билет «годен → подтверждён», если арбитраж разрешил |
| Отмена с возвратом | Жизненный цикл удержания | Перевести билет «подтверждён → отменён» и вернуть место |
| Срок годности 5 минут | Жизненный цикл удержания | Переводить просроченные билеты «годен → просрочен» |

## 3. Анализ обязанностей

Проверка связности: компонент делает только своё дело.

| Компонент | Знает | Не знает |
|---|---|---|
| Витрина доступности | Окно устаревания и его последствия; владеет кэшем доступности и его инвалидацией (слушатель сброса — часть Витрины) | Как вычисляется остаток; как работает арбитраж; как меняются состояния билетов |
| Выдача удержаний | Как выдать билет ровно один раз | Кто решает вместимость; что происходит с билетом после выдачи |
| Арбитраж вместимости | Доменное правило 6 — и только его | Кто и как показывает остаток; что такое идемпотентность |
| Жизненный цикл удержания | Машину состояний билета: годен, подтверждён, отменён, просрочен | Сколько мест у слота и как это решается |

Витрина читает остаток, но **владельцем знания о вместимости остаётся Арбитраж** — витрина лишь транслирует. Если витрина узнает больше, чем нужно для показа, это сигнал к переносу знания (закон Деметры).

**Проверка на ловушку для сущностей**: ни один компонент не «управляет» остальными. Арбитраж решает, но не знает, кто и зачем спрашивает. Свойство поддерживает масштабируемость: Витрина и Выдача, обслуживающие всю толпу, не проходят через точку сериализации.

## 4. Анализ архитектурных характеристик

| Компонент | Характеристики |
|---|---|
| Арбитраж вместимости | **Целостность (1)**, производительность (4) — самая дефицитная точка системы, здесь конкурируют все |
| Витрина доступности | **Масштабируемость (2)**, согласованность (7) — здесь всплески чтений |
| Выдача удержаний | Производительность (4), защищённость (5: идентификатор билета неугадываем) |
| Жизненный цикл удержания | Целостность (1, совместно с арбитражем), тестируемость (6: машина состояний тестируется без окружения) |
| Осуществимость (3) | Сквозная: четыре компонента укладываются в один репозиторий и в заданные классы |

## 5. Связанность CA / CE / CT

```
          ┌──────────────────────┐
          │  Витрина доступности │
          └──────────┬───────────┘
                     │ читает остаток (знает арбитраж)
                     ▼
          ┌──────────────────────┐
          │  Арбитраж вместимости│◄──────────────────────┐
          └──────────▲───────────┘                       │
                     │ спрашивает разрешение             │
                     │                                   │
          ┌──────────┴───────────┐          ┌────────────┴─────────┐
          │  Жизненный цикл      │◄────────►│  Выдача удержаний    │
          └──────────────────────┘          └──────────────────────┘
                     ▲                                   ▲
                     └── общая сущность «билет» ─────────┘
                        (словарь состояний общий, связи вызовов нет)
```

| Компонент | CA | CE | CT |
|---|---|---|---|
| Витрина доступности | 0 | 1 | 1 |
| Арбитраж вместимости | 2 | 0 | 2 |
| Жизненный цикл удержания | 1 | 1 | 2 |
| Выдача удержаний | 1 | 1 | 2 |

Ребро «Выдача ↔ Жизненный цикл»: вызовов между компонентами нет, но по определению книги компоненты связаны, если изменение одного может потребовать изменения другого. Словарь состояний билета общий: изменится статусная модель — изменятся оба. Ослабленная связь через общую сущность, а не через знание о процессе.

Ребра «Жизненный цикл → Витрина» в графе нет намеренно: сброс кэша после подтверждения и отмены устроен событием (ADR 0006). Жизненный цикл публикует факт `SlotChanged` и не знает ни о кэше, ни о его слушателях — знание о кэше остаётся у Витрины, которая его показывает. Общий словарь события — слабая связь той же природы, что и ребро «билет».

**Арбитраж — единственный, кого не сломать изменением остальных**, проверка «what if»:

| Изменение | Затрагивает |
|---|---|
| Витрина перестаёт кэшировать | только витрину |
| Билеты получают новое состояние | выдачу и жизненный цикл, не арбитраж и не витрину |
| Модель вместимости меняется с вычисляемой на счётчик | только арбитраж — жизненный цикл не заметит |
| Появляется квота на клиента | только выдачу |

Знание распределено по владельцам; применять закон Деметры не к чему — распределение уже минимально, а общий CT системы переносом не уменьшается.
