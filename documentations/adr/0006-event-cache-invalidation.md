# 0006. Инвалидация кэша событием, а не прямым вызовом

- **Статус:** Accepted
- **Дата:** 2026-08-28
- **Связанные ADR:** [[0004-cache-read-only]]

## Контекст
После подтверждения и отмены кэш доступности должен сбрасываться — и только после фиксации изменений. Связать Жизненный цикл удержания с кэшем можно двумя способами: прямым вызовом сброса либо публикацией факта об изменении.

## Решение
Жизненный цикл после коммита публикует факт `SlotChanged`. Слушатель `InvalidateAvailabilityCache` — часть Витрины доступности — сбрасывает кэш. Жизненный цикл не знает ни о кэше, ни о слушателях.

## Почему (альтернативы)
Прямой вызов сброса из Жизненного цикла добавляет ребро «Жизненный цикл → Витрина» в граф связанности шага 2 и переносит знание о кэше от его владельца (Витрины) к постороннему компоненту. Событие — факт, публикатор не знает слушателей (гл. 11, производные события): граф связанности не меняется, правило ADR 0004 держится и здесь — кэш по-прежнему не участвует в решении, только в обслуживании.

## Последствия
Стало проще: знание о кэше в одном месте; новые реакции на изменение слота добавляются слушателями без правки Жизненного цикла.

Стало сложнее: сброс проходит через событийный механизм — на один файл больше, отладка на один шаг длиннее.

Пересмотрим, если сброс потребуется сделать синхронной частью операции (требование свежести выше, чем даёт окно кэша).
