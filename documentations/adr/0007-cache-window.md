# 0007. Окно кэша доступности: две фазы и защита от лавины

- **Статус:** Accepted
- **Дата:** 2026-08-28
- **Связанные ADR:** [[0004-cache-read-only]], [[0006-event-cache-invalidation]]

## Контекст
ТЗ требует кэшировать результат на 5–15 секунд с защитой от cache stampede. Диапазон из двух границ допускает два прочтения: фиксированный TTL в интервале либо окно из двух фаз. Лавина в системе возникает в двух разных моментах — естественное истечение ключа и инвалидация после записи, причём инвалидация совпадает по времени с пиком интереса к слоту.

## Решение
Окно кэша — две фазы: до 5 с данные свежие; до 15 с — допустимо устаревшие, отдаются мгновенно с фоновым обновлением (stale-while-revalidate, в Laravel — `Cache::flexible(key, [5, 15])`). Защита от лавины — по моментам: при естественном истечении лавины нет в принципе — старое значение отдаётся, обновление одно на всех; при инвалидации старого значения нет, поэтому первое наполнение кэша берётся атомарной блокировкой (`Cache::lock`), остальные читатели ждут его результат.

## Почему (альтернативы)
Фиксированный TTL задаётся одним числом, а не диапазоном — требование «5–15 с» указывает на окно. Только блокировка без двух фаз: при естественном истечении читатели ждали бы регенерацию вместо мгновенного ответа. Только две фазы без блокировки: после инвалидации нет устаревшего значения, чтобы отдать, — всплеск промахов транслировался бы в БД.

## Последствия
Стало проще: читатель не ждёт БД ни в одном из сценариев; число обращений к БД не зависит от числа читателей.

Стало сложнее: два механизма вместо одного; устаревание до 15 с — осознанная цена, названная заказчиком в секундах (характеристика 7).

Пересмотрим, если потребуется свежесть строже 5 с на пути записи.
