# 0005. «SlotService» из ТЗ — сервисный слой, а не класс

- **Статус:** Accepted
- **Дата:** 2026-08-28
- **Связанные ADR:** [[0003-layered-style]]

## Контекст
Техническое задание требует «Service layer: SlotService», который обрабатывает транзакции, кэш и идемпотентность. Буквально это читается как один класс с тремя разнородными обязанностями; один класс заваливает принципы проекта (код под unit-тесты, CQS — команды и запросы смешаются).

## Решение
«SlotService» трактуется как сервисный слой — каталог `app/Services`. Четыре логических компонента шага 2 реализуются отдельными классами: `AvailabilityReader`, `HoldCreator`, `CapacityArbiter`, `HoldLifecycle`. Класса с именем `SlotService` нет.

## Почему (альтернативы)
Один класс `SlotService` — god object: транзакции, кэш и идемпотентность в одном месте не тестируются без полного окружения. Фасад `SlotService` над четырьмя компонентами — слой-прокладка и лишние рёбра связанности без выгоды: контроллерам достаточно одного-двух соратников.

## Последствия
Стало проще: каждый класс тестируется отдельно, обязанности не смешаны.

Стало сложнее: ревьюер, читающий ТЗ буквально, может искать класс `SlotService`. Соответствие фиксируется явной строкой в README.

Пересмотрим, если приёмка потребует класс с точным именем.
