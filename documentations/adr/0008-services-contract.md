# 0008. Контракт сервисного слоя: один сервис — один `handle()`

- **Статус:** Accepted
- **Дата:** 2026-08-31
- **Связанные ADR:** [[0005-slot-service-directory]], [[0003-layered-style]]

## Контекст
ADR 0005 определил сервисный слой как каталог `app/Services` с четырьмя компонентами, но не задал форму классов. При реализации компоненты получили по нескольку публичных методов (`HoldLifecycle`: confirm и cancel; `CapacityArbiter`: ensureCapacity и reserve), а команда создания возвращала данные. Форма контрактов была разной от класса к классу.

## Решение
Один сервис = один публичный контракт, метод называется `handle()`. Каталог разбит на домены: `Slots` (Витрина доступности + Арбитраж вместимости) и `Holds` (Выдача удержаний + Жизненный цикл). Команды не возвращают данные (CQS); единственное исключение — фабричный контракт создания `CreateHold::handle(): Hold` (создание и возврат сущности — атомарная операция, контроллеру нужен билет и флаг новизны).

## Почему (альтернативы)
Класс с несколькими контрактами — тот же god-object, что отклонил ADR 0005, только внутри одного компонента: обязанности смешиваются, тесты крупнее. Разное именование (create/confirm/reserve) заставляло ревьюера каждый раз угадывать форму. Единый `handle()` и имя-глагол класса («что делает») делают форму предсказуемой: действие → класс → `handle()`.

## Последствия
Стало проще: единая форма контрактов, каждый сервис тестируется отдельно, DI-соглашение очевидно.

Стало сложнее: число классов выросло (4 компонента → 8 сервисов); каждое новое действие — новый класс, что при большом росте предметной области даст много файлов.

Пересмотрим, если действие обзаведётся естественными под-операциями с общим состоянием — тогда группировка в домен, а не в класс.
